## 3. Session store and per-account lookup

- [x] 3.1 Added `AccountRegistry` (`crates/server/src/session.rs`) holding `accounts: RwLock<HashMap<String, Arc<AccountSession>>>` on `ServerState`, with `get(account_key)` (lookup-only) and `insert(session)` (used by sign-in to register or replace an account's live session). Deliberately not a "get-or-create-from-DB" as originally sketched: `AccountSession::sign_in` already builds a fully-authenticated session from the cookie in one step, so the only place a new entry is ever created is a successful sign-in registering it — a bare lookup never fabricates one. A session naming an account_key with no live entry (sign-out, or a restart since) is correctly treated as stale, matching the server's pre-existing "sign in again after a restart" behavior.
- [x] 3.2 `RequireSession::from_request_parts` resolves session id → `account_key` → `AccountRegistry::get` (removing the old single `state.app.it.is_logged_in()` global check), rejecting as unauthenticated when missing or when the resolved account isn't logged in, and hands back the resolved `Arc<AccountSession>`. Covered by `tests.rs`'s integration tests (a live account succeeds; a signed-out/absent one is rejected with 401).
- [x] 3.3 Every route handler taking `RequireSession` (library.rs, playlists.rs, ratings.rs, settings.rs, lastfm.rs, auth.rs's gated routes, media.rs's `register_play`, ws.rs's `upgrade`) now builds a `Scoped`/`ScopedOwned` from the resolved session (via `RequireSession::scoped`/`scoped_owned`) and passes that into the matching `commands::*` function. `cargo build -p server` succeeds with no remaining direct reads of a single global `InnerTube` or unscoped per-account settings/plays call.
- [x] 3.4 `browse.rs`, `search.rs`, and `blocked.rs` remain anonymous/ungated exactly as before — confirmed no `RequireSession` was added to any of their routes; their former `state.app.it` calls now read `state.shared.anonymous_it`.

## 4. Sign-in / sign-out isolation

- [x] 4.1 `POST /api/auth/cookie` calls `commands::auth::sign_in` (builds a fresh, fully-authenticated `AccountSession` from the cookie), registers it into `AccountRegistry` via `insert` (replacing any prior entry for the same `account_key`, never touching any other account's), and mints a session id scoped to that account_key. Verified by `tests.rs`'s `settings_are_isolated_between_concurrently_signed_in_accounts` (two concurrently live accounts, synthetic rather than signed in over real network — see 4.3's note).
- [x] 4.2 `POST /api/auth/signout` removes only the calling session from `SessionStore` (`sessions.remove(session_id)`, resolved from the request's own cookie header — not `clear()`), and evicts the `AccountSession` from `AccountRegistry` only once `sessions.any_session_for(account_key)` is false. Verified by `tests.rs`'s `signing_out_one_session_does_not_affect_another`.
- [x] 4.3 The `http-auth` spec's concurrent-sign-in/sign-out scenarios are covered by `crates/server/src/tests.rs`'s integration tests, with one deliberate substitution: tests use a synthetic, locally-"signed-in" `AccountSession` (a fake cookie string, which is all `InnerTube::is_logged_in` ever checks) instead of a real cookie-paste sign-in through `/api/auth/cookie`, because a genuine sign-in requires a live YouTube account cookie this environment doesn't have (same constraint 7.3 already notes). This exercises every isolation-relevant code path (`RequireSession`, `AccountRegistry`, `SessionStore`, the route handlers) without needing one; only the network call inside `AccountSession::sign_in` itself is unexercised here.
